# 强弱双模型对比 — deepseek-v4-flash vs deepseek-v4-pro

自建集 20 题，temperature 0，各跑 3 次（DeepSeek 无 sampling seed，单次
跑分是噪声，故一律报区间）。2026-08-19。

## 结果

| 指标 | v4-flash（弱） | v4-pro（强） |
|---|---|---|
| 首次执行通过率 | 11–13/18（61–72%） | **14–15/18（78–83%）** |
| 自修正后通过率 | 17–18/18（94–100%） | 16–18/18（89–100%） |
| 口径标注命中 | 2–3/4 | **3–4/4** |
| 追问行为正确率 | **4/4（三跑全对）** | **4/4（三跑全对）** |
| 每题 token（in+out） | 3,122–3,582 | 2,987–3,094 |
| prompt 缓存命中率 | 88–90% | 86–89% |
| 每题耗时 | 3.9–4.3s | 6.1–6.5s |
| 每题成本（上限估计） | $0.0007–0.0008 | $0.0019–0.0020 |

## 差异出现在哪里

**强模型赢在"一次写对"，不赢在"最终答对"。** 首次通过率差了约 15 个百分
点（61–72% → 78–83%），但自修正后两者收敛到同一区间。分解到 case 上：
`multi_channel_user_ranking`、`metric_active_buyers_last_month` 两题两个
模型都要探索一轮才对；flash 额外在 `no_clarify_plain_order_count`、
`metric_gmv_paid_last_month` 上多绕一次。

**这正是架构贡献与模型贡献的分界线**：自修正闭环把一个弱模型的最终准确率
拉到了强模型水平，代价是多一轮工具调用（也就是 token 与延迟）。换句话说，
**这套架构用 1/3 的钱买到了同等的最终正确率**，牺牲的是首答率。

**追问判断与模型强弱无关**：两个模型三跑全部 4/4。追问是由系统提示里的
三步决策协议 + 只在命中 caution 口径时才注入指引共同决定的——这是提示工程
的产物，不是模型能力的产物。反过来说，如果这条也随模型波动，就说明我的
触发准则写得不够硬。

**口径标注是强模型唯一稳定占优的地方**（3–4/4 vs 2–3/4）：在回答里正确
援引口径名需要模型同时完成"用对定义"和"说明用了哪个定义"，弱模型经常
做对前者、漏掉后者。这是提示可以再收紧的地方，但属于表述要求而非正确性。

## 成本与延迟的取舍

pro 贵 2.7 倍、慢 50%，换来的是首答率 +15pp 和更稳的口径标注。对本项目的
目标用户（小数据团队的交互式取数），**flash + 自修正**是更划算的默认：
用户等待 4.3s 拿到正确答案，比等 6.2s 拿到同样正确的答案更好。

值得注意的是 pro 的每题 token **更少**（少绕路），所以 2.7 倍的成本差完全
来自单价而非用量。

## 缓存命中率 88–90%

系统提示（schema + 命中口径 + 工具定义）在一次问答的多轮之间完全不变，
被 DeepSeek 的 prefix cache 命中。命中价比未命中便宜约 30 倍，因此这
9 成命中率把实际成本压到了名义单价的很小一部分——如果 context 组装顺序
不稳定（例如把变化的内容放在前缀），这个杠杆会立刻消失。
