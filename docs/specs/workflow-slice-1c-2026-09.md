# 切片 1C：统计区间进入 SQL（结构化映射与类型化编译）

日期：2026-09-10。状态：计划（验收标准在实现前固定）；已于 v0.7.0 实现，结果见 §8。承接 v0.6.0。

## 1. 为什么做这一刀

v0.6.0 的结果行下面有一句"系统不核对两者是否一致"。它最刺眼的实例是时间：用户问
「上个月新增用户有多少」，确认单上写着「统计周期：按自然月」，执行的却是全量
`COUNT(*)`——问题里的时间从来没进过 SQL。那句免责说明是诚实的，但它说明产品在最常见
的一类取数上答的不是用户问的问题。

1A 的编译器是一张 `(指标, 口径) → 整条 SQL` 的查找表，注释里写着"1C 用真正的
QueryPlan 编译器替换它"。这一刀就是那一步，但只做最窄的一截：**统计区间**。

## 2. 已定的设计取舍

| 编号 | 取舍 | 理由 |
|---|---|---|
| C01 | 类型化编译，不扩展 Connector 做参数绑定 | 交接文档 §11.3 明确允许首个切片这样做。进入 SQL 的只有两类值：维护者写的 SQL 片段（可信配置，走 PR 评审），以及解析器产出的 `date` 对象。**用户原话永远不进 SQL。** 参数绑定要改三种方言与 agent 工具路径，另立一刀 |
| C02 | 新增结构化规则键 `period`（统计区间），与文档的 `time_window`（统计周期约定）分开 | `time_window` 是一句话（"按自然月"），解释口径；`period` 是一个绝对区间，进 SQL。混在一个键里，文档一句话就能覆盖用户问的区间 |
| C03 | `period` 只能来自用户：问题里的时间表述，或 `--period` / 交互输入 | 抽取的允许键不含 `period`，**文档无法注入统计区间** |
| C04 | 确定性解析器，只认一个封闭集合；多个不同区间、或不可能的日期，一律当缺口 | 时间歧义就是口径歧义（§9.3）。认不出就问，不猜 |
| C05 | 相对表述在准备草案时按 `workflow.timezone`（默认 Asia/Shanghai）换算成绝对日期，写进哈希 | 明天执行时跑的仍是今天确认的区间，不会随日期漂移（§9.3） |
| C06 | 映射改为结构化（`from` / `measure` / `time_column` / `where` / `label`）；旧的整条 `sql:` 仍可用，但**遇到统计区间就拒绝** | §11.2："超出支持形态时返回当前映射不支持"，不静默忽略区间 |
| C07 | 结果行只列真正编译进 SQL 的规则（选定口径、统计区间）；其余规则仍在免责说明里 | 延续 v0.6.0 的诚实原则：只声称执行了的 |

## 3. 对接方必读

- `period` 的规则值是规范串 `2026-08-01..2026-08-31`（含首尾），进内容哈希；确认单显示为
  「2026-08-01 至 2026-08-31」并注明换算自问题里的哪几个字。
- 编译出的条件是半开区间，边界是**裸日期**：`time_column >= 'start' AND time_column < 'end+1'`。
  不用 `'start 00:00:00'`：SQLite 里纯日期文本 `'2026-08-01'` 按字典序小于它，会漏掉区间第一天
  （见 T34 补记）。
- 时区：数据按**数据库存储的本地时间**比较；`workflow.timezone` 只决定"今天"是哪天。
  存储时区与业务时区不同的部署，本切片不处理。
- 映射里的 `measure` / `where` 是维护者 SQL 片段，被原样拼进语句；它们与整条 `sql:` 享有
  相同的信任级别，编译结果照旧经过 `safety.ensure_safe_select`。`from` 与 `time_column`
  必须是标识符，加载时校验。

## 4. 支持的时间表述（封闭集合）

| 表述 | 区间（今天 = 2026-09-10，周四） |
|---|---|
| 上个月 / 上月 | 2026-08-01 至 2026-08-31 |
| 本月 / 这个月 | 2026-09-01 至 2026-09-10（截至今天） |
| 上周 | 2026-08-31 至 2026-09-06（周一起算） |
| 本周 | 2026-09-07 至 2026-09-10 |
| 昨天 / 前天 / 今天 | 单日 |
| 去年 / 今年 | 整年 / 截至今天 |
| 最近 N 天 / 近 N 天 / 过去 N 天 | 含今天在内的 N 天 |
| 2026年8月 / 2026-08 | 整月 |
| 8月 | 最近一个不在未来的 8 月 |
| 2026-08-15 / 2026年8月15日 | 单日 |
| 2026-08-01..2026-08-15（或 到 / 至 / ~） | 显式区间 |

"本月""本周""今年"都截至今天，"最近 N 天"含今天——这些是口径选择，确认单上以绝对日期
展示，由人确认。

## 5. 不变量与验收

| 编号 | 不变量 |
|---|---|
| P1 | 问题里的单一时间表述被换算为绝对区间，以「本次约定」出现在确认单上，并注明来源字样 |
| P2 | 两个不同区间、或不可能的日期（2026-02-30）→ 不自动填写；若指标要求区间，列为缺失 |
| P3 | 区间写进内容哈希：确认后改区间使旧确认失效；**确认后第二天执行，跑的仍是确认时的日期** |
| P4 | 文档抽取无法产生 `period`（不在允许键内） |
| P5 | 结构化映射把区间编译进 WHERE；SQLite / MySQL / ClickHouse 上结果与手写参照查询一致 |
| P6 | 整条 `sql:` 映射遇到区间 → 拒绝执行（不忽略区间）；没有区间时照旧可用 |
| P7 | 没有任何用户字符串进入编译出的 SQL（用含引号与注释的恶意问句验证） |
| P8 | 结果行列出选定口径与统计区间；免责说明不再列这两项 |
| P9 | 指标不要求区间且问题没给时，结果行明写"未限定统计区间"，不是静默全量 |
| P10 | 聚合在区间内没有记录时（SUM 返回 NULL），明说"该区间没有匹配记录"，不显示成 0 或裸 NULL |

测试：`tests/test_periods.py`（解析，固定"今天"，含跨年、闰年、周起始）；
`tests/test_query_compiler.py`（编译与拒绝）；扩充 `test_workflow_service.py`（P3）、
`test_cli_flow.py`（P1/P2/P8/P9/P10）、`test_workflow_end_to_end.py`（区间后的真实数字）；
`test_mysql_integration.py` / `test_clickhouse_integration.py` 各加一条 P5。

## 6. 风险与回滚

- 全部是加法：旧的 `sql:` 映射行为不变（除非遇到区间，那时它本来就是错的）。回滚点 `v0.6.0`。
- 维护者 SQL 片段被拼接：信任级别与改动前的整条 `sql:` 相同，不是新的注入面；用户输入
  只以 `date` 形式进入，是新的也是唯一的一类值。
- 演示数据止于 2026-08-22，"上个月"是不完整月。本切片不处理数据截止日期，只在演示说明里写明。

## 7. 明确不承诺

按天 / 维度分组（"上个月每天"）；多区间对比；参数化绑定；财年与自定义日历；存储时区
换算；把文档里"按自然月"之类的约定与用户给的区间做一致性校验（仍在免责说明里）。

## 8. 实施结果（2026-09-10）

状态：**已实现**，本地与三方言集成测试通过，T32–T35 关闭。

- P1–P10 全部有测试；546 passed / 1 skipped（基线 466）。
- 三方言：编译出的区间查询，在 MySQL 上与 `DATE_FORMAT`、在 ClickHouse 上与 `toYYYYMM`
  的原生月份过滤结果一致；SQLite 端到端用 `strftime` 独立参照。
- 真机（演示库，DeepSeek 抽取文档规则）：「上个月新增用户」注册口径执行
  `created_at >= '2026-08-01' AND created_at < '2026-09-01'`，得 5812，与参照一致；
  「上个月成交额」支付口径 49,771,870.26，一致；「成交额」不给时间 → 统计区间列为缺失、
  拒绝执行；「本月成交额」→ 明说结果为空而不是印一个 NULL。
- **实施中发现的真缺陷**：`'YYYY-MM-DD 00:00:00'` 形式的下界让 SQLite 里纯日期文本的
  区间首日整日漏算。改为裸日期（见 T34 补记）。
- **超出计划的必要改动**：演示映射结构化、结果行把区间计为已执行、端到端测试改用真实演示
  映射——少一件，提交之间就是坏的（见 T33）。

仍不承诺的，见 §7；其中"数据截止日期"在真机上已经看得见：演示数据止于 08-22，「上个月」
在 9 月问是不完整月，系统目前说不出来。
