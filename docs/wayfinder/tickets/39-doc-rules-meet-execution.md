# T39 — 文档依据与执行的口径互相核对

## Question

确认单上「文档依据：按注册日期计数」与执行的「首单口径」可以同时出现，结果行只能说"系统
不核对两者是否一致"。文档规则不能成为 SQL（信任边界），但它可以经由维护者声明的映射，
确定性地对应到某个可执行口径。

## Work

- 映射条目 `enforces: {规则键: [字眼]}`；已验证的逐字引文命中某映射的字眼 → 规则与该口径
  对应（`implies`）；同时命中两组互斥字眼 → 不声称对应。
- 文档依据一致指向唯一口径时草案直接带上它（文档依据 + 出处）；采用某份文档写法后自动得到
  对应口径，与之矛盾的 `--variant` 拒绝。
- 确认单逐条标注：已执行 / 与所选口径不一致 / 未核对；结果行据此计入或点名。

## Done when

- F11–F14，真机（DeepSeek 抽取）：只有运营手册时草案直接带上注册口径；运营与增长手册分歧
  时采用任一写法即得到对应口径；故意选相反口径时确认单与结果行都点名不一致。

## Resolution（2026-09-11）

- **对应是确定性的**：维护者在映射上声明 `enforces: {规则键: [字眼]}`；已通过逐字校验的
  引文里出现某口径的字眼，即与之对应。原文从被引切片里按偏移读回，不取模型给的字符串。
  多个口径共享同一字眼（两种新增用户都排除测试账号）＝都施加；两组互不相交的字眼同时出现
  （「不按注册日期，按首单日期」）＝不声称。
- **文档进入 SQL 的唯一通道是"选择"**：文档依据一致指向唯一口径时，草案带上它（文档依据 +
  出处），仍需用户确认；有未决分歧时不预选，否则采用另一边就会与之矛盾。采用某份文档写法后
  自动得到对应口径；同一条命令里与之矛盾的 `--variant` 拒绝、不执行任何查询；单独的
  `--variant` 可以推翻文档，推翻后确认单与结果行都点名。
- 结果行：已执行的文档规则计入执行口径；不一致的单独一句"注意"；没有对应字眼的仍在
  "不核对"说明里——那句话终于只用于真的无法核对的规则。
- `implies` 只在非空时进入内容哈希：v0.7 记录的确认对旧草案仍然成立（有逐字节对照测试）。
- 真机（DeepSeek 抽取，演示库）：
  - 只有运营手册：注册口径被预选为文档依据，5812；统计口径与过滤条件计入执行口径。
  - 同上但 `--variant first_order`：确认单 ✗、结果"注意"点名统计口径，3559。
  - 运营 + 增长手册分歧：两种写法各注"对应可执行口径"；采用增长手册写法后不再追问，
    直接跑首单口径，3559。
  - finance 身份问成交额、选支付口径：财务说明的金额口径与退款处理对应净额口径，被点名不
    一致；过滤条件没有声明字眼，留在"不核对"里。
- **实施中改掉的**：预选口径后确认单仍写"需要你选一个"；结果行里文档规则的句号接分号。
- **review 补记**：矛盾拒绝原来只在 CLI，服务层现在也拒绝同一次补充里的矛盾；对应判定改为
  "独有词"（只有一种口径有独有字眼时归它）；`implies` 只在非空时落盘，v0.7 仍能读新草案。
- 词表设计的教训写进了演示映射：净额口径不能用「扣除」，因为「不扣除退款」也含它，而命中
  两组字眼的引文按设计不声称任何对应。
