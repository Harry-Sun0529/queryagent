# T33 — 统计区间进入草案与确认

## Question

区间要以「本次约定」出现在确认单上、写进哈希、第二天执行不漂移；指标要求区间而问题
没给时，要列为缺失并让用户补。

## Work

- `PERIOD_RULE_KEY` 进 models；`required_rules` 可声明 `period`，但抽取允许键不含它（P4）。
- `MetricDraftBuilder` 注入"今天"（按 `workflow.timezone`），从问题解析区间。
- CLI `--period`，交互补写走同一个解析器，认不出就拒绝。
- 确认单把区间显示为「2026-08-01 至 2026-08-31」并注明换算自哪几个字。

## Done when

- P1、P2、P3、P4 有测试；P3 用注入时钟证明"今天确认、明天执行"跑的是确认时的日期。

## Resolution（2026-09-10）

P1–P4 全部有测试。问题里唯一的时间表述被换算为绝对区间，以「本次约定」出现在确认单上，
并注明「由问题中的「上个月」换算」；两个不同区间或不可能的日期让区间列为缺失——**即使
指标并不要求区间**，因为问题明明问了一个区间，不带区间去跑等于回答了另一个问题。
区间写进内容哈希：用注入时钟证明 9-10 确认、10-02 执行，跑的仍是 8 月。
`required_rules` 可声明 `period`，但抽取的允许键不含它，文档无法设置区间。

范围比票面多了三件，因为少一件提交之间就是坏的：

- **演示映射改为结构化**。否则「上个月新增用户」一带上区间，整条 SQL 映射会（按 T34 的
  设计）拒绝执行，演示直接不可用。
- **结果行把统计区间算作已执行**（P8 提前做）。否则免责说明会把一个真的编进 SQL 的区间
  也列为"不核对"——那句说明本身就不诚实了。
- **端到端测试改用仓库里真实的演示映射**，固定"今天"为 2026-09-10，参照数用 SQLite 的
  `strftime` 独立计算，不拿编译器的半开边界自证。

**实施中发现 T34 的真缺陷**：SQLite 里纯日期文本 `'2026-01-01'` 按字典序小于
`'2026-01-01 00:00:00'`，下界把区间第一天整日排除了。是这里的 CLI 夹具让计数变成 0 才
暴露——T34 自己的边界测试每行都带时分秒。边界改为裸日期，补测试，详见 T34 补记。

另：`--period` 显式指定时覆盖问题里的区间；认不出的写法直接拒绝并列出能认的写法——打了
字却没被理解的区间，绝不能悄悄变成"没有区间"。`workflow.timezone`（默认
Asia/Shanghai）只决定"今天"，不换算存储时间；未知时区在加载配置时拒绝。
