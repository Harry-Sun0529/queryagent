# v0.3.0 — 可观测性、成本工程与系统性提升

## Destination

一个 v0.3.0 tag（**暂不推送**，等人工找 bug 后再发），让这个项目能回答
Agent / AI 应用岗最常问的三类问题：**生产环境怎么 debug 一个 agent**、
**它每个问题花多少钱多久**、**你如何系统性地提升它而不是碰运气**。

## Notes

- **本 effort 把 execution 纳入 map**（覆盖 wayfinder 的 plan-don't-do
  默认值）：路线已在前一轮 grilling 中厘清，tickets 承载的是可执行工作
  而非待决策问题；因此单 session 可连续 resolve 多个 ticket。
- 目标函数：**面试可辩护深度优先**（主投 Agent / AI 应用开发岗），
  可用度做到「能用起来」档。
- 遵循 skills：`tdd`（在预先声明的 seam 上先红后绿）、`code-review`
  （双轴，Standards + Spec，本 map 即 Spec 源）、`codebase-design`。
- **铁基线（每次改动必须不回退）**：自建集 首次 15/18 · 自修正后
  17–18/18 · 追问行为 4/4。任一指标掉了就回滚该改动。
- **改进手段边界**：只允许动 prompt 与 context 策略。若失因分析指向
  架构问题，停下来带证据向人类申请授权，不擅自扩边界。
- **锚点纪律**：seed 42 的 30 题是封存 test 集，只在 T8 跑一次；
  seed 7 的新 dev 集才允许分析与迭代。
- 唯一可用模型：DeepSeek（`deepseek-v4-flash` 弱 / `deepseek-v4-pro`
  强）。key 从环境变量读，永不进 git。

## Decisions so far

<!-- one line per closed ticket -->

- [T1 — usage 透传与 UsageEvent](tickets/01-usage-event.md) — usage 走新增的
  `UsageEvent`（不污染语义事件），厂商字段差异在 backend 内消化；实测
  prompt 缓存命中率首轮 22%、之后稳定 ~81%。
- [T2 — Trace 落盘与 replay](tickets/02-trace-replay.md) — 事件流落 JSONL，
  按 field 逐个反序列化以兼容字段增减；默认开 + stderr 提醒 + gitignore
  三重隐私处理，`replay` 全量还原。
- [T3 — 成本、延迟与缓存命中进 eval 报告](tickets/03-cost-latency-report.md) —
  分档定价 + 未知模型报 n/a 不猜；peak/off-peak 不自动判定（不可复现），
  统一按上限计。
- [T4 — 友好错误提示](tickets/04-friendly-errors.md) — 顶层 `_explain()`
  产出「问题 + 怎么修」两行，退出码 2，`--verbose` 保留 traceback。
- [T10 — 支持 DeepSeek 思考模式](tickets/10-thinking-mode.md) — v4 系列的
  `reasoning_content` 必须回传，否则第二轮工具调用必 400；由 eval 跑分
  回归抓出（单测与单轮 ask 均无法暴露）。
- [T5 — 强弱双模型对比](tickets/05-dual-model.md) — 强模型赢在首答率
  (61-72%→78-83%)，自修正后收敛；自修正闭环以 1/3 成本换到同等最终正确率。
  追问判断与模型强弱无关（提示工程的产物）。

## Not yet specified

- 若失因分析指向架构缺陷（而非 prompt/context），是否申请扩边界到
  「可改架构」——需带证据与人类重新协商。
- prompt cache 命中率若显著偏低，是否值得为「稳定前缀」重排 context
  组装顺序（成本优化 vs 复杂度）。
- v4-pro 若显著优于 flash，默认配置是否切换（涉及成本/质量取舍与
  README 数字口径）。
- 失因分析可能揭示自建集本身的用例缺陷，届时是否补充/修订用例。
- 是否把思考模型的 `reasoning_content` 也暴露为事件（trace 可见性 vs
  噪声与体积）——当前只作协议管道，不进事件流。
